RAPPORT D'IMPLEMENTATION - INGESTION DE RAG-UNIVERSAL
Date : 2026-11-23

1. ARCHITECTURE EXISTANTE EXAMINEE

Le depot implemente une API FastAPI avec SQLAlchemy, PostgreSQL, des modules
Auth, Identity, Credentials et Users. L'authentification existante emet des JWT
dont le type distingue un administrateur d'Identity d'un User. La dependance
get_authenticated_user verifie le token, le Credential, l'Identity et le User
cote serveur. Le modele Ingestion et sa migration etaient deja presents dans
les changements locaux au debut de cette mission; ils relient deja chaque
ingestion au couple (identity_id, user_id).

Les routes/services/modeles/tests des modules concernes ont ete examines.
Aucune documentation existante du projet n'a ete consulte pour determiner le
perimetre.

2. FONCTIONNALITES D'INGESTION DEVELOPPEES

- Creation d'une ingestion PENDING puis reception binaire en flux jusqu'a
  RECEIVED, ou passage a FAILED avec un code et un message non sensible.
- Reception du texte brut, de fichiers individuels, de fichiers CSV/JSON et
  d'autres extensions configurees.
- Support extensible des source_type; les sources locales et WEB peuvent
  transmettre un identifiant de source.
- Limite de taille configurable, calcul SHA-256, type detecte cote serveur,
  dates et emplacement temporaire relatifs.
- Validation des extensions, noms, contenus texte, JSON/XML, archives DOCX/ODT
  et marqueurs PDF. Le MIME annonce par le client n'est pas utilise.
- Consultation paginee des propres ingestions et telechargement authentifie
  de la source originale.
- Les fichiers de meme nom ont des identifiants et emplacements differents;
  la publication du fichier final ne peut pas ecraser un fichier existant.

3. ROUTES AJOUTEES

- GET /api/v1/ingestions/folder-client : client navigateur local.
- POST /api/v1/ingestions : cree les metadonnees d'une reception.
- PUT /api/v1/ingestions/{ingestion_id}/source : recoit le contenu binaire en
  streaming, sans le parser ni le stocker entierement en memoire.
- POST /api/v1/ingestions/text?document_name=... : recoit du texte brut en
  streaming.
- GET /api/v1/ingestions : liste les ingestions du User courant.
- GET /api/v1/ingestions/{ingestion_id} : retourne les metadonnees du
  proprietaire uniquement.
- GET /api/v1/ingestions/{ingestion_id}/source : restitue la source originale
  au proprietaire uniquement.

4. MECANISME LOCAL D'ACCES AUX DOSSIERS

Le client servi par FastAPI utilise l'API navigateur showDirectoryPicker().
Le navigateur ouvre son dialogue natif; apres la selection, l'utilisateur
confirme une seconde fois avant le parcours et l'envoi. Le client parcourt
recursivement les handles du dossier choisi, verifie leur appartenance par
root.resolve(), et transmet chaque fichier separement. Il ne connait ni
n'accede au disque du serveur comme s'il s'agissait du disque local.

Les chemins envoyes sont relatifs au dossier autorise. Les chemins hors racine,
les liens/refus d'acces signales par le navigateur et les fichiers caches sont
refuses localement. Le serveur ne recoit aucun chemin absolu local.

5. AUTORISATION EXPLICITE

La page ne conserve le token que dans la memoire de la page, efface le champ du
mot de passe apres la connexion, demande une selection native du dossier et
exige une confirmation avant de parcourir son contenu. Les resultats par
fichier distinguent recus, refuses et erreurs.

6. AUTHENTIFICATION

Aucune authentification n'a ete reimplementee. Les routes utilisent
get_authenticated_user. Les tokens d'administrateur Identity et les tokens
User sont distincts; un token administrateur ne permet pas l'ingestion.
L'Identity, le User et le Credential proviennent du contexte JWT verifie et de
la base, jamais d'un identity_id/user_id declare par le client.

7. ISOLATION IDENTITY/USER

Les requetes de lecture filtrent simultanement sur l'Identity et le User
authentifies. Une ingestion d'un autre proprietaire renvoie 404. La dependance
refuse les tokens invalides/expirés, les credentials desactives, les Identity
desactivees et les Users desactives. La cle etrangere composite du modele
Ingestion protege egalement l'association Identity/User.

8. STOCKAGE TEMPORAIRE

Le stockage temporaire est separe du Knowledge Storage, lequel n'a pas ete
cree. L'organisation des fichiers est :
<racine>/<identity_id>/<user_id>/<ingestion_id>/<nom>.
Les repertoires sont limites aux permissions 0700 et les fichiers aux
permissions 0600. Les chemins sont controles contre les traversals et liens
symboliques. Aucun endpoint ne supprime une source originale apres reception.

La commande `python -m app.modules.ingestion.cleanup` ne supprime que les
fichiers partiels .part- anciens et marque comme FAILED les receptions PENDING
ou RECEIVING abandonnees qui n'ont pas de source finale. Elle ne supprime
aucune source finale ni les metadonnees des ingestions recues.

11. CONFLITS AVEC LE CODE EXISTANT

Le depot ne contenait pas de client frontend. Le choix demande a l'utilisateur
a ete le client navigateur minimal servi par FastAPI. Le test existant de
tables Identity a ete actualise pour tenir compte de la table Ingestion.

Les modifications locales initiales dans app/core/config.py et
migrations/env.py, ainsi que le modele/migration Ingestion non suivis, ont ete
conserves et integres. La methode preexistante delete_relative_path, qui
permettait la suppression arbitraire d'une source, a ete retiree du stockage;
le nettoyage est limite aux fichiers partiels.

12. PROBLEMES NON RESOLUS

- Il n'y a pas de recuperation serveur de pages Web a partir d'une URL. Le type
  WEB accepte une URL HTTPS comme metadonnee et peut recevoir les octets d'une
  source via l'API generique, mais aucun connecteur ne telecharge l'URL. Un
  fetcher arbitraire expose a des risques SSRF; il necessite une politique de
  destinations publiques, DNS, redirections et limites de transfert.
- Le client dossier exige un navigateur supportant showDirectoryPicker et un
  contexte securise (HTTPS ou localhost). Aucun client CLI de remplacement
  n'est fourni.
- Le parcours navigateur a ete valide avec des handles simules; l'ouverture
  reelle du dialogue du systeme d'exploitation n'a pas ete automatisee.
- Les formats DOCX/ODT sont controles structurellement sans extraction; aucune
  extraction/normalisation du contenu n'est realisee.
